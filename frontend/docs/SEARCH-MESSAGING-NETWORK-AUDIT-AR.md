# تدقيق طلبات البحث والمحادثات — 8 نوفمبر 2026

## ما يثبته سجل Network

- طلبات `GET /search` بأنواع `products`, `stores`, `ads`, `services` تمثل مجموعات نتائج منفصلة عند التنقل بين تبويبات البحث. لا تُدمج لأن النتائج والفلاتر مختلفة.
- طلب `GET /search/suggestions` يتكرر مع تغيّر النص. سجلات `ERR` بلا HTTP status غالبًا تتوافق مع إلغاء طلب قديم بعد تغيّر الاستعلام، لكنها لا تثبت وحدها أن كل الأخطاء إلغاء؛ يلزم فحص `error.name/code` أو سجلات الخادم لتمييز AbortError عن فشل الشبكة.
- `GET /messages/:id/messages?limit=50` يجلب الرسائل الفعلية، بينما `/messages/:id?_rsc=...` طلب تنقل/مكوّنات Next.js. لا يوجد دليل أنهما طلبان مكرران لنفس المورد.
- طلبات `POST /conversations/:id/messages` ذات التوقيتات والمعرّفات المختلفة لا تثبت إعادة إرسال الرسالة نفسها؛ لا يمكن استنتاج التكرار من URL وحده دون operation id أو message id.
- `GET /notifications/unread-count` طلب مشترك لجرس الإشعارات في واجهة التطبيق، وليس بالضرورة طلبًا خاصًا بصفحة المحادثة.
- بحث `type=services` استغرق 3165ms؛ يحتاج قياس SQL/Prisma على الخادم قبل تعديل الاستعلام أو إضافة فهارس.

## التعديل الآمن

- زيادة مهلة debounce لاقتراحات البحث من 300ms إلى 500ms لتقليل عدد البادئات الوسيطة المرسلة أثناء الكتابة.
- عدم تشغيل الاقتراحات أثناء اختلاف النص الخام عن النص المؤجل، حتى لا تُعرض اقتراحات قديمة أثناء الكتابة.
- تطبيع المسافات وحالة الأحرف في مفتاح React Query وقيمة الطلب، بما يتوافق مع مفتاح Redis غير الحساس لحالة الأحرف في الخادم.
- الإبقاء على حد الحرفين ومدة الكاش 60 ثانية.

## حدود التحقق

لا تتوفر في بيئة العمل dependencies داخل `frontend/node_modules`، لذلك لم تُشغّل Vitest أو `tsc --noEmit` أو بناء Next.js. يجب تنفيذها بعد دمج التعديل.
