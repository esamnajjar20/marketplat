# MarketPlat — تجميع طلبات API (المرحلة الثانية)

## النطاق

تستهدف هذه المرحلة شاشة **خدماتي → النظرة العامة وقائمة خدماتي**. أظهر فحص مسار التهيئة أن ملف مقدم الخدمة يُحمّل أصلًا ضمن `GET /users/me/bootstrap` ويُزرع في React Query؛ لذلك لا نعيد جلبه من endpoint التجميع ولا نعتبره طلبًا زائدًا يجب استبداله.

الطلبان المستقلان اللذان تحتاجهما الشاشة فعليًا هما:

- إحصائيات مقدم الخدمة: `GET /service-providers/me/analytics?period=all`.
- صفحة خدمات المستخدم: `GET /service-listings/me?page=1&limit=10` مع معاملات الحالة والبحث والترقيم عند استخدامها.

## التغيير

أُضيف endpoint محمي:

```http
GET /api/v1/service-providers/me/dashboard?period=all&page=1&limit=10
```

وتُضاف إليه عند الحاجة معاملات `status` و`search`. الاستجابة تجمع:

```json
{
  "analytics": {},
  "listings": {
    "items": [],
    "meta": {}
  }
}
```

يستخدم المسار `authenticate` و`CACHE.NONE` لأن البيانات خاصة بصاحب الحساب. ويتم التحقق من `period/page/limit/status/search` بواسطة Zod schema مخصص. يُحلّ ملف البائع ومقدم الخدمة مرة واحدة، ثم تُنفّذ قراءات الإحصائيات وقراءة صفحة الخدمات بالتوازي. واستعلامات صفحة الخدمات نفسها تنفّذ جلب العناصر والعدّ بالتوازي داخل repository.

## ربط الواجهة ومنع التكرار

- `MyServicesHub` و`MyServiceListingsList` يستعملان `useMyServiceProvider()` للحصول على هوية مقدم الخدمة من كاش bootstrap عند توفرها.
- المكوّنان يشتركان في `useMyServiceProviderDashboard`، مع معاملات URL موحّدة (`page/status/q`) ومفتاح React Query واحد؛ فلا ينفذ كل مكوّن طلبًا منفصلًا.
- استجابة النظرة العامة تتضمن الإحصائيات وقائمة الخدمات المعروضة في الصفحة نفسها؛ تغيير البحث/الحالة/الصفحة يطلب بيانات الصفحة المطلوبة من endpoint نفسه بدل فصل الإحصائيات عن القائمة.
- مفتاح الـ dashboard يتضمن `userId` والفترة ومعاملات القائمة، لمنع تداخل نتائج مستخدمين أو فلاتر مختلفة.
- تُخزّن الإحصائيات في مفتاحها user-scoped أيضًا؛ لذلك يمكن لتبويب الإحصائيات إعادة استخدام فترة `all` عند فتحه ما دامت النتيجة حديثة. الفترتان `7d` و`30d` تبقيان كسولتين ولا تُحمّلان قبل فتح التبويب.
- بيانات الملف الشخصي لا تُكرر في استجابة التجميع، وبيانات المواعيد والطلبات الواردة والتبويبات الأخرى لا تُحمّل مسبقًا.

## تحديث الكاش

أُبقي إبطال `workspaceDashboardRoot` بعد عمليات الخدمات والطلبات والمواعيد التي قد تؤثر في الإحصائيات أو قائمة الخدمات. كما يُبطل مفتاح الإحصائيات المنفصل كي تبقى شاشة التحليلات متسقة.

## الأثر المتوقع على عدد الطلبات

في الزيارة التي لا تتطلب تحديث bootstrap، كان المكوّنان يطلبان الإحصائيات وقائمة الخدمات كلٌّ على حدة (طلبان API)، بالإضافة إلى احتمال جلب ملف مقدم الخدمة إذا لم يكن bootstrap قد زرعه في الكاش. الآن تُحمّل الإحصائيات والقائمة في طلب dashboard واحد، ويُعاد استخدام ملف مقدم الخدمة من bootstrap/cache. لا يعني ذلك إزالة طلب bootstrap العام، ولا دمج بيانات لا يحتاجها المستخدم في تلك اللحظة.

عند تغيير فلاتر القائمة مع بقاء الإحصائيات ضمن مدة صلاحيتها، يعيد hook استخدام الإحصائيات المحفوظة ويطلب صفحة الخدمات وحدها من `/service-listings/me`؛ فلا يعيد تنفيذ القراءات التحليلية السبعة لكل تغيير صفحة أو بحث. إذا كانت الإحصائيات غير موجودة أو منتهية الصلاحية أو أُبطلت بعد طفرة، يعود hook إلى endpoint المجمّع ويحدّث القيمتين معًا.

## الفحوص

تم تحديث `api-batching-phase2-audit.mjs` لفحص عقد analytics + listings، وحماية المسار، وتوحيد معاملات URL ومفتاح المستخدم، والإبطال بعد الطفرات. فحص transpile للصياغة لا يغني عن تشغيل اختبارات Jest/Vitest أو `npm run type-check` أو البناء الكامل؛ يجب تشغيلها في بيئة المشروع التي تحتوي dependencies.

## التحقق بعد النشر

افتح `/my-services` على حساب لديه ملف مقدم خدمة. المتوقع:

- ألا ينفذ المكوّنان طلبين منفصلين للإحصائيات و`/service-listings/me`.
- ظهور طلب واحد إلى `/service-providers/me/dashboard?period=all&page=1&limit=10` عند فتح النظرة العامة.
- بقاء `GET /users/me/bootstrap` لأنه مصدر ملف مقدم الخدمة وبيانات تهيئة التطبيق.
- عند البحث أو تغيير الحالة أو الصفحة، يتشارك المكوّنان نفس query؛ ومع بقاء الإحصائيات حديثة يظهر طلب قائمة واحدة فقط، وعند انتهاء صلاحية الإحصائيات يُستخدم dashboard المجمّع لتحديثهما معًا.
- لا تُحمّل بيانات المواعيد والطلبات الواردة قبل فتح تبويباتها.

هذا التقرير يصف تصميم الكود المتوقع؛ القياس الحي بعد النشر ما زال مطلوبًا.
