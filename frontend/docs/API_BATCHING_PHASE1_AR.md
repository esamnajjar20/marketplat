# MarketPlat — تجميع طلبات API (المرحلة الأولى)

## نطاق التنفيذ

بدأ التنفيذ بمسار صفحة المتجر العامة لأنه يحتوي مجموعة بيانات صغيرة ومترابطة تظهر في رأس الصفحة نفسه: بيانات المتجر، الشارات، حالة متابعة المتجر، وحالة إضافته للمفضلة.

أضيف endpoint واحد:

```http
GET /api/v1/stores/:id/page-data
```

ويعيد بنية من الشكل التالي:

```json
{
  "store": {},
  "badges": [],
  "viewer": {
    "isFollowing": false,
    "isFavorited": false
  }
}
```

تكون `viewer` بقيمة `null` للزائر غير المسجّل. لا يحتوي الرد على بيانات اعتماد أو حقول خاصة إضافية.

## ما تغير

- جُمعت قراءة المتجر والشارات وحالتي المتابعة والمفضلة في استدعاء واحد من الواجهة.
- تُنفّذ قراءتا المتابعة والمفضلة بالتوازي داخل الباك إند، وتُحسب الشارات اعتمادًا على سجل المتجر الذي جرى تحميله بدل طلب بيانات المتجر مرة أخرى.
- يستخدم `StoreHeader` الطلب المجمّع في مسار الصفحة الأساسي، وليس مسار الاسترداد فقط.
- إذا نجح الطلب المجمّع، تُمنع طلبات الشارات والمتابعة والمفضلة المنفصلة. الطلبات الفردية تبقى مسار احتياط عند فشل الطلب المجمّع حيث يلزم.
- استُبدل تحميل قائمة المتاجر المتابَعة كاملة من أجل فحص متجر واحد بفحص مستهدف، وأصبحت حالة المتابعة المجمّعة هي المصدر الأساسي لرأس المتجر.
- مفاتيح React Query الخاصة بالرد المجمّع تتضمن معرّف المستخدم، لمنع إعادة استخدام حالة متابعة/مفضلة مستخدم آخر بعد تبديل الحساب.
- استجابة endpoint عليها `CACHE.NONE` لأنها تشمل حالة خاصة بالمستخدم، ولا يجوز تخزينها في كاش مشترك بين المستخدمين.
- يستخدم middleware المصادقة الاختيارية تحققًا كاملًا من Bearer token عند وجوده، ويعامل الطلب كزائر عند غياب التوكن أو عدم صلاحيته؛ endpoint نفسه يظل عامًا.

## حماية سلوك عداد المشاهدات

صفحة Server Component الأساسية تجلب المتجر أصلًا عبر `GET /stores/:id`، وهذا المسار مسؤول عن زيادة عداد المشاهدات. لذلك لا يرفع endpoint المجمّع العداد افتراضيًا.

مسار الاسترداد في `StoreDetailClient` فقط يرسل `trackView=true`، لأنه يعوّض فشل تحميل الصفحة من الخادم. أضيفت اختبارات تؤكد أن القراءة المجمّعة العادية لا تضاعف الزيارة، وأن مسار الاسترداد يسجلها مرة واحدة.

## ما تُرك منفصلًا عمدًا

- المنتجات والعروض والمجموعات والإعلانات: تُحمّل عند فتح التبويب المعني فقط. جمعها كلها عند فتح صفحة المتجر سيزيد حجم البيانات ويكسر التحميل الكسول.
- التوصيات: لا تُطلب من مسار الاسترداد الذي لا يعرض قسم التوصيات.
- عداد الإشعارات: بيانات عامة مشتركة في شريط التنقل؛ الأفضل معالجتها كبيانات تطبيق مشتركة بدل إدخالها في رد خاص بالمتجر.
- صفحة قائمة المتاجر التي يتابعها المستخدم: ما زالت تحتاج قائمتها؛ لم يُحذف endpoint القائمة من الاستخدام الصحيح.

## الأثر المتوقع

في رأس صفحة المتجر، تتحول قراءات الشارات والمتابعة والمفضلة المنفصلة إلى طلب API مجمّع واحد عند نجاحه. كما لا يجري تحميل قائمة تصل إلى 100 متجر لمجرد معرفة حالة متجر واحد.

هذا يقلل عدد رحلات الشبكة من المتصفح، لكنه لا يثبت وحده مقدار تحسن زمن الاستجابة أو عدد استعلامات قاعدة البيانات في بيئة الإنتاج. يجب قياس ذلك بعد النشر من Network وقياسات الباك إند.

### فحص غير ناجح معروف

`prefetch-policy-audit.mjs` لا ينجح في النسخة الحالية: وجد 358 رابطًا بدل 362 بحسب manifest الموجود، مع اختلافات في `MyRequestOffersPageClient` و`MyRequestsPageClient` و`RequestsPageClient`. هذا الفحص لا يتعلق بتجميع طلبات صفحة المتجر، ولم أغيّر تلك الصفحات ضمن هذه المرحلة.

لم تُشغّل اختبارات Vitest/Jest أو `npm run type-check` أو بناء Next.js؛ مجلدا `frontend/node_modules` و`apps/api/node_modules` غير موجودين في الأرشيف. فحص الصياغة ليس بديلًا عن فحص الأنواع أو البناء.

## النطاق اللاحق

هذه المرحلة تنفذ التجميع على رأس صفحة المتجر فقط، وليست ادعاءً بأن كل طلبات المشروع قد جُمعت. الخطوة التالية هي جرد مجموعات الطلبات المتزامنة في صفحات الملف الشخصي وخدماتي ولوحات الحساب، ثم اختيار مجموعات مماثلة فقط عندما تكون بياناتها مطلوبة معًا وتشارك حدود صلاحيات وكاش متوافقة.
