# تقليل طلبات RSC عند تغيير الفلاتر على مستوى MarketPlat

## الهدف

تقليل طلبات Next.js App Router / React Server Components (`?_rsc=...`) التي لا تضيف بيانات لازمة عندما يغيّر المستخدم فلترًا أو ترتيبًا أو نوعًا أو تبويبًا داخل الصفحة نفسها، بينما النتائج تُحمّل أصلًا من المتصفح عبر React Query.

**لم يتم إلغاء طلبات API اللازمة لإحضار نتائج الفلتر الجديد.** عند اختيار مدينة أو حالة أو ترتيب جديد، قد يبقى طلب API واحد ضروري لإحضار النتائج، أو قد تُستخدم نتيجة موجودة في كاش React Query. الذي جرى منعه هو طلب RSC الإضافي لنفس الصفحة عندما لا تحتاج الصفحة إلى إعادة تنفيذ Server Component.

## الآلية المشتركة

1. استخدام `writeClientUrl()` من `frontend/lib/urlWithParams.ts` لأزرار الفلاتر التي تقرأ حالتها من `useSearchParams()` وتجلب النتائج من العميل.
2. إضافة الخاصية `clientQueryNavigation` إلى `IntentPrefetchLink`. عند النقر العادي على رابط من نفس الـ origin ونفس pathname، إذا كان الاختلاف في query فقط، يُمنع تنقل Next ويُحدّث العنوان عبر History API. تظل روابط المسارات الأخرى وروابط `target="_blank"` والتنزيلات ونقرات Ctrl/Cmd/Shift كما هي.
3. في صفحات التصفح العامة، تقرأ شبكات النتائج قيم URL الحية. لا يُعاد استعمال `initialPage` القادم من SSR إلا عندما تتطابق معاملات URL الحالية مع المعاملات التي أُنشئت منها البيانات الأولية؛ هذا يمنع عرض نتائج الفلتر السابق بعد التغيير المحلي.

## نطاق الصفحات والمكونات التي غُطّيت

### التصفح العام والبحث

- الإعلانات: شرائح التصنيفات، الفلاتر، ترتيب النتائج، إعادة تعيين نتائج البحث.
- المنتجات والمتاجر والخدمات: الفلاتر والتصنيفات وعرض الشبكة/القائمة والبحث والترتيب.
- البحث الموحد: صندوق البحث، شرائح النوع، الفلاتر السريعة، السمات، نطاق الموقع، ورقة الفلاتر، إزالة الفلاتر واقتراحات البحث.
- الطلبات المفتوحة: نوع الطلب، المدينة، مجال الخدمة، البحث والترتيب.
- رسائل النجاح التي تنظف معاملات URL مؤقتة دون إعادة جلب صفحة RSC.

### صفحات المستخدم والطلبات

- «طلباتي» و«عروضي»: تبويبات حالات الطلبات والعروض.
- طلبات الخدمة الخاصة بالمستخدم: تغيير الحالة وإصلاح عنوان الصفحة عند خروج رقم الصفحة عن النطاق.
- «خدماتي»: تم الحفاظ على آلية الفلاتر المحلية القائمة للطلبات الواردة والمواعيد وقوائم الخدمات.
- إدارة المتجر: المنتجات، التوفر، المخزون، البحث والترتيب.
- واجهة المتجر العامة: تبويبات الواجهة والبحث والترتيب داخل المنتجات.
- المفضلة: اختيار القائمة ونوع العناصر.
- تبويبات الملف الشخصي.

### الإدارة

- فلاتر المستخدمين والإعلانات والمتاجر وسجل العمليات والبلاغات.
- شريط الفلاتر الإداري المشترك.
- روابط طابور العمل وأحدث النشاط التي تفتح قسم الإدارة مع فلتر حالة جاهز.
- روابط التنقل بين أقسام لوحة الإدارة؛ هذه الأقسام تُعرض داخل صفحة `/admin` نفسها وتقرأ `useSearchParams`.
- روابط شريط التصفح العام والخاص التي تغيّر نوع نتائج `/search` أثناء وجود المستخدم في صفحة البحث نفسها، وروابط «عرض الإعلانات» في حالة عدم وجود نتائج؛ أصبحت تحديثات query محلية بدل طلب RSC.
- تأكيد التعامل المحلي مع روابط التبويب داخل لوحات `/my-store` و`/my-services` و`/activity` و`/settings` و`/account/sales` و`/offline` عبر معالجات الـ hub الموجودة، وعدم تكرار منطق التنقل داخل كل قائمة.

### مكوّن الرابط المشترك

- `IntentPrefetchLink` يدعم `clientQueryNavigation` بشكل opt-in فقط؛ لم يتم تغيير كل الروابط عالميًا حتى لا تتأثر الانتقالات الحقيقية إلى صفحات أخرى.
- أضيفت اختبارات للتحقق من تحديث query محليًا، وبقاء التنقل الطبيعي عند تغيير المسار أو استخدام النقر المعدّل.

## ما بقي كما هو عمدًا

- الانتقال من صفحة إلى صفحة أخرى، مثل فتح تفاصيل إعلان أو خدمة أو طلب.
- الانتقال إلى تسجيل الدخول أو إنشاء عنصر جديد أو إكمال إجراء يؤدي إلى صفحة مختلفة.
- اختيار تصنيف يؤدي إلى مسار تصنيف مستقل مثل `/categories/:slug`.
- أي طلب API يحتاجه المستخدم فعلًا للحصول على نتائج الفلتر المختار.
- عمليات SSR التي تعتمد فعليًا على معاملات الخادم؛ لا يجري تجاوزها آليًا.

## نتائج الفحص وحدوده

- تم تحليل صياغة TypeScript/TSX لجميع ملفات المصدر والاختبار التي تغيرت في هذه المرحلة بعد التوسعة النهائية: **0 أخطاء صياغة**.
- جرت محاولة تشغيل `tsc --noEmit`، لكنها لم تكن قابلة للاعتماد لأن نسخة العمل لا تحتوي `node_modules`؛ وظهرت أخطاء عدم العثور على `react` و`next/navigation` و`axios` وأنواعها، ما أدى إلى أخطاء متسلسلة في JSX والاستدلال على الأنواع.
- لم يتم تشغيل Vitest/Jest أو بناء Next للإنتاج في هذه البيئة؛ الاختبارات الجديدة مضافة ولكن لم أدّع نجاح تشغيلها.
- التحقق النهائي من انخفاض `?_rsc` وقياس عدد طلبات API يتطلب نشر الملفات ثم تسجيل Network أثناء استخدام كل صفحة. التوقع هو اختفاء RSC الزائد لتغييرات query في المكونات التي عولجت، مع بقاء طلب API اللازم عند تغير النتائج.
