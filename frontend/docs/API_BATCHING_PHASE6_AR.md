# المرحلة السادسة — تجميع طلبات صفحة العملاء

## النتيجة

كانت صفحة `frontend/components/sales/CustomersPageClient.tsx` تطلب عند فتحها:

- `GET /customers` لعرض أول صفحة من العملاء (50 عنصرًا).
- `GET /customers/summary` لبطاقات إجمالي العملاء وVIP والمدينين وغير النشطين وإجمالي/متوسط المشتريات.

أضيف `GET /customers/overview` ليعيد `summary` و`customers` في استجابة واحدة. ينفذ الباك إند عمليتي القراءة بالتوازي عبر `Promise.allSettled`، مع الإبقاء على استعلامات المستودع الحالية كما هي. هذا يعزل الفشل الجزئي: إذا تعذر الملخص تظل القائمة متاحة، وإذا تعذرت القائمة تظل بيانات الملخص متاحة، وتُرسل مؤشرات فشل منفصلة للواجهة.

## سلوك البحث والتحديث

- الفتح الأول: طلب HTTP واحد للملخص وأول صفحة.
- عند إدخال بحث: طلب قائمة مستقل بالمعامل `q`، ولا يعاد طلب الملخص.
- عند مسح البحث: تعود الصفحة إلى بيانات النظرة العامة المخزنة في TanStack Query، مع احترام `staleTime` البالغ 30 ثانية.
- عمليات إنشاء/تحديث العميل تُبطل كاش النظرة العامة والقوائم والبحث والملخص كي لا تبقى الأرقام أو النتائج قديمة.
- المسار محمي بالمصادقة، ولا يضيف كاش HTTP مشتركًا لبيانات العملاء الخاصة.

## الحدود

هذا يقلل اتصالات HTTP من 2 إلى 1 عند فتح الصفحة فقط. لا يدمج استعلامات SQL داخل قاعدة البيانات؛ ما زالت قراءة الملخص والقائمة منفصلتين وتنفذان بالتوازي. كما لم يتم تغيير تفاصيل العميل أو البحث الدقيق أو صفحات المبيعات الأخرى.

## التحقق

شغّل `node scripts/api-batching-phase6-audit.mjs` من مجلد `frontend`. هذا تدقيق عقد ثابت، وليس اختبار تشغيل أو بديلًا عن `tsc` أو اختبارات Jest.
