# محاكي المستخدمين الحقيقي — MarketPlat

محرك Playwright مستقل يشغّل جلسات Chromium منفصلة على واجهة MarketPlat المنشورة. لوحة التحكم موجودة في `/admin?tab=user-simulator` وتعمل عبر API backend، ولا يتصل المتصفح الإداري مباشرة بمحرك Playwright ولا يحصل على مفتاحه السري.

## البنية

- `tools/user-simulator`: خدمة Node.js مستقلة لتشغيل Chromium وحفظ الإعدادات والتقارير ولقطات الشاشة.
- `apps/api/src/modules/platform/user-simulator`: طبقة وسيطة محمية بمصادقة MarketPlat وصلاحية `ADMIN` على الأقل.
- `frontend/components/admin/AdminUserSimulatorPanel.tsx`: لوحة إعداد التشغيل وإدارة السيناريوهات ومتابعة النتائج.

لا تشغّل Chromium داخل Cloudflare Worker. انشر هذه الخدمة على خادم Linux يدعم Node.js 22+ وChromium، أو على VM/Container مستقل. لا تفترض أن بيئة Termux أو خطة استضافة محدودة الذاكرة ستستطيع تشغيل العدد نفسه من المتصفحات.

## التثبيت

من جذر monorepo:

```bash
npm run simulator:install
npm run simulator:browser:install
```

على Ubuntu/Debian عند نقص مكتبات Chromium النظامية، ثبّت تبعيات المتصفح مرة واحدة وفق صلاحيات الخادم:

```bash
cd tools/user-simulator
npx playwright install-deps chromium
```

## إعداد محرك Playwright

انسخ:

```bash
cp tools/user-simulator/.env.example tools/user-simulator/.env
```

أنشئ مفتاحًا عشوائيًا:

```bash
openssl rand -hex 32
```

ضع القيمة نفسها في `SIMULATOR_ADMIN_TOKEN` على خادم المحاكي و`USER_SIMULATOR_RUNNER_TOKEN` في بيئة `apps/api`. لا تضع هذه القيم في الواجهة الأمامية أو ملفات Git.

أهم إعدادات المحرك:

| المتغير | الوظيفة |
|---|---|
| `SIMULATOR_ADMIN_TOKEN` | سر اتصال API backend بمحرك المتصفح، 32 حرفًا على الأقل |
| `SIMULATOR_TARGET_URL` | أصل الموقع المنشور المراد اختباره |
| `SIMULATOR_ALLOWED_HOSTS` | قائمة أسماء المضيفين المسموح بها، مفصولة بفواصل ومن دون بروتوكول |
| `SIMULATOR_HARD_MAX_USERS` | الحد الأعلى لعدد المستخدمين في التشغيل الواحد، الافتراضي 100 |
| `SIMULATOR_HARD_MAX_CONCURRENCY` | الحد الأعلى لجلسات Chromium المتزامنة، الافتراضي 20 |
| `SIMULATOR_HARD_MAX_WRITE_USERS` | الحد الأعلى الافتراضي للمستخدمين في سيناريوهات الكتابة على الإنتاج، الافتراضي 5 والحد الأعلى 20 |
| `SIMULATOR_DATA_DIR` | مكان حفظ إعدادات المحاكي والسيناريوهات |
| `SIMULATOR_REPORT_DIR` | مكان حفظ تقارير JSON ولقطات PNG |
| `SIMULATOR_TEST_ACCOUNTS` | حسابات موجودة مسبقًا لتجارب الدخول، كـ JSON |
| `SIMULATOR_EMAIL_TEMPLATE` | قالب بريد إنشاء حساب جديد، مع `{runId}` و`{user}` و`{iteration}` |
| `SIMULATOR_TEST_PASSWORD` | كلمة مرور حسابات التسجيل التجريبية |

مثال لقائمة حسابات اختبار مخصصة (حساب منفصل لكل مستخدم افتراضي ولكل دور):

```dotenv
SIMULATOR_TEST_ACCOUNTS=[{"email":"buyer1@your-domain.example","password":"BUYER_QA_PASSWORD","role":"buyer"},{"email":"seller1@your-domain.example","password":"SELLER_QA_PASSWORD","role":"seller"}]
```

لتشغيل سيناريو تسجيل الحساب، استخدم نطاق بريد تملكه وتستطيع استقبال رسائل التحقق عليه:

```dotenv
SIMULATOR_EMAIL_TEMPLATE=qa+{runId}-{user}-{iteration}@your-domain.example
SIMULATOR_TEST_PASSWORD=USE_A_UNIQUE_TEST_PASSWORD
```

التسجيل في النظام يرسل رسالة تحقق. سيناريو التسجيل الحالي يتحقق من إنشاء الحساب والدخول الأولي فقط؛ لا يدّعي التحقق من البريد. العمليات التي تشترط حسابًا موثقًا تحتاج حسابات QA تم التحقق منها مسبقًا في `SIMULATOR_TEST_ACCOUNTS`. يجب توفير حساب مستقل لكل مستخدم افتراضي في سيناريوهات الدخول. السيناريوهات المصنفة `accountRole: buyer` تحتاج حسابات بدور `buyer`، وسيناريوهات `accountRole: seller` تحتاج حسابات بدور `seller`. لا يمكن جمع دوري المشتري والبائع في تشغيل واحد؛ شغّل كل دور في دفعة مستقلة. الحسابات القديمة التي لا تحتوي `role` تعامل كحسابات `any` للسيناريوهات العامة فقط.

## تشغيل الخدمة والربط مع API

شغّل محرك المتصفح:

```bash
npm run simulator:start
```

للتشغيل المحلي على نفس الخادم، اترك `SIMULATOR_HOST=127.0.0.1`. إذا كان محرك المتصفح على خادم منفصل، اربطه خلف HTTPS reverse proxy أو شبكة خاصة موثوقة. لا تكشف منفذ HTTP مباشرة للإنترنت. عند الحاجة إلى استقبال اتصالات من reverse proxy على الخادم نفسه، اضبط `SIMULATOR_HOST=0.0.0.0` مع حجب المنفذ عن الإنترنت واستخدام TLS عند نقطة الدخول.

في بيئة `apps/api` اضبط:

```dotenv
USER_SIMULATOR_RUNNER_URL=https://your-private-runner.example
USER_SIMULATOR_RUNNER_TOKEN=THE_SAME_RANDOM_TOKEN
```

يجب أن يكون الرابط هو أصل الخدمة من دون `/api`. المتغيران اختياريان، لكن يجب ضبطهما معًا. في الإنتاج يقبل API عنوان HTTPS فقط.

بعد نشر الواجهة وAPI وإعادة تشغيل API، افتح:

`/admin?tab=user-simulator`

يجب أن يكون المستخدم `ADMIN` أو `SUPER_ADMIN`. صلاحية المحاكي لا تظهر لـ`MODERATOR` ولا تعتمد على إخفاء الواجهة فقط؛ API نفسه يفرض الدور.

## معنى عدد المستخدمين والتزامن

- **المستخدمون الافتراضيون (Virtual Users):** إجمالي الجلسات التي ستنفذ السيناريو.
- **المتصفحات المتزامنة (Browser Concurrency):** عدد جلسات Chromium التي تعمل في اللحظة نفسها فعليًا.
- **Ramp-up:** توزيع بداية المستخدمين على فترة زمنية.
- **Think time:** وقفة بين خطوات المستخدم لمحاكاة سرعة التفاعل البشرية.
- **Iterations:** عدد مرات إعادة السيناريو لكل مستخدم.

مثال: 50 مستخدمًا افتراضيًا و5 متصفحات متزامنة = 5 جلسات تعمل معًا، ويستكمل المحرك باقي المستخدمين على دفعات. لا تبدأ بتزامن كبير على الموقع المنشور: ابدأ بـ1 ثم 2–5، وراقب CPU وذاكرة خادم المتصفح وخدمات MarketPlat قبل الزيادة. حتى لو كان حد القراءة أعلى، تظل السيناريوهات التي تكتب بيانات محدودة افتراضيًا إلى 5 مستخدمين افتراضيين لكل تشغيل (يمكن لمسؤول الخادم رفع الحد إلى 20 عبر متغير البيئة). العدد العالي يستهلك موارد خادم Chromium وقد يخلق حملًا إنتاجيًا حقيقيًا.

## السيناريوهات القابلة للتوسعة

أضف/عدّل السيناريو من لوحة الإدارة كـ JSON. المحرك لا ينفذ JavaScript حرًا أو `eval`. الخطوات المدعومة:

- `goto`: الانتقال لمسار داخلي يبدأ بـ`/` فقط.
- `click`, `clickText`, `fill`, `select`, `check`, `uncheck`.
- `hover`, `press`, `scrollIntoView`.
- `clickRole`, `clickDialogRole`, `fillRole`, `pressRole`, `expectRoleVisible` للتعامل مع العناصر وفق أدوار الوصول وأسمائها بدل CSS. `clickRole` يدعم `optional: true` لتجاوز زر لا يظهر إذا كانت العملية منجزة مسبقًا. `selectFirstOption` يختار أول عنصر متاح في قوائم الاختيار المخصصة.
- `upload`: اختيار ملف اسمه فقط من `tools/user-simulator/fixtures`، ويتطلب `writes: true`.
- `expectVisible`, `expectHidden`, `expectText`, `expectUrl`, `expectNotUrl`.
- `wait`, `screenshot`.

مثال بسيط لسيناريو قراءة:

```json
{
  "id": "search-basic-check",
  "name": "فحص البحث الأساسي",
  "description": "فتح البحث والتحقق من ظهور حقل البحث.",
  "enabled": true,
  "writes": false,
  "requiresAccount": false,
  "tags": ["search", "read-only"],
  "steps": [
    { "type": "goto", "value": "/search" },
    { "type": "expectVisible", "selector": "body" },
    { "type": "screenshot", "fullPage": false }
  ]
}
```

يُفضّل استخدام `data-testid` مستقرة في مكونات الواجهة عند تأليف السيناريوهات، بدل الاعتماد على نصوص العرض القابلة للتغيير.

## رحلات الأعمال الجاهزة

تتضمن السيناريوهات الافتراضية رحلات تم بناء محدداتها من اختبارات E2E الموجودة في المشروع، وليس من أسماء عناصر مفترضة:

- زائر: تصفح الصفحة الرئيسية والإعلانات والمنتجات والخدمات والمتاجر والبحث والتصنيفات.
- مشتري: تسجيل الدخول التلقائي، الصفحات الخاصة، البحث وحفظ البحث، إضافة إعلان QA للمفضلة، متابعة بائع QA، وإرسال رسالة إلى بائع QA.
- بائع: فتح مساحات العمل، إضافة عميل CRM، إنشاء إعلان QA بصورته التجريبية، وتعديل إعلان/منتج/خدمة مخصصة للاختبار.
- تسجيل الحساب: إنشاء حساب مستقل باسم وبريد مشتقين من القالب. هذا السيناريو منفصل عن سيناريوهات الحسابات الموجودة، ولا يكرر التسجيل في iteration واحد.

سيناريوهات المفضلة/المتابعة/المراسلة تحتاج `SIMULATOR_SEED_AD_ID` أو `SIMULATOR_SEED_SELLER_ID`. تعديل الكيانات يحتاج `SIMULATOR_SEED_PRODUCT_ID` و`SIMULATOR_SEED_SERVICE_ID` أيضًا. هذه القيم يجب أن تشير إلى سجلات QA فعلية منشورة ومملوكة للحساب المناسب. لا توجد IDs تجريبية افتراضية في الكود.

إنشاء الإعلان ينشر محتوى QA حقيقيًا على الموقع المنشور؛ لذلك يظهر فقط بعد تفعيل السماح بالكتابة، ويجب استخدام حساب بائع QA. ملف الصورة المرفق `marketplat-qa-image.png` صورة اختبار واضحة، لا تستخدم صورة مستخدم.

لا تغطي السيناريوهات الافتراضية كل نموذج وميزة في المنصة تلقائيًا. أضف الرحلات المتخصصة عبر محرر السيناريوهات بعد توفير حسابات وبيانات QA مناسبة. لا تستخدم تعديلات محتوى إنتاجي مهم كاختبار.

## حماية الموقع المنشور

- المحرك يقبل المضيفين المسجلين فقط في `SIMULATOR_ALLOWED_HOSTS`، ويمنع التنقل إلى أصل خارجي من سياق المتصفح.
- تشغيل سيناريو يكتب بيانات يحتاج إلى موافقة تشغيل صريحة من لوحة الإدارة (`writes: true` ثم تفعيل سماح بيانات QA).
- خطوات الحذف/الدفع/الاسترداد أو أي خطوة معرفة كـ`risk: "destructive"` مرفوضة على الموقع المنشور. ويمنع المحرك أيضًا ضغطات النقر التي تبدو أسماؤها حساسة.
- لا توجد عمليات تنظيف تلقائية لحسابات أو سجلات الإنتاج؛ سجلات QA تبقى في قاعدة البيانات إلى أن تُدار يدويًا وفق سياسة المنصة.
- لا تضف حسابات حقيقية أو كلمات مرور مستخدمين حقيقيين. استخدم حسابات اختبار مخصصة فقط.

المحاكي يختبر واجهة المستخدم الفعلية؛ ليس بديلًا عن k6 أو اختبارات API المعتمدة لقياس RPS/throughput. عدد جلسات المتصفح المتزامنة يقيس رحلات المستخدم وطلبات الشبكة الناتجة عنها، ولا يساوي عدد طلبات API في الثانية.

## التقارير والمخرجات

لكل تشغيل تقرير JSON يتضمن:

- إجمالي المستخدمين، من بدأ/اكتمل/فشل.
- كل خطوة واسم المستخدم والسيناريو والمسار والمدة والنتيجة.
- DOMContentLoaded وLCP ووسيط/ P95 لأزمنة التحميل.
- عدد طلبات API وأكواد HTTP وأزمنة الاستجابة الكاملة ومتوسط/P95.
- أخطاء Console وJavaScript وفشل الشبكة.
- لقطات شاشة عند فشل الرحلات، قابلة للتنزيل من لوحة الإدارة.

الإعدادات والسيناريوهات والتقارير تحفظ على قرص محرك المتصفح. في خدمة مستضافة، اربط مجلد البيانات/التقارير بقرص دائم أو انسخ التقارير خارجيًا؛ التخزين المؤقت للخدمة قد يُحذف عند إعادة النشر أو إعادة إنشاء الحاوية.

## الاختبارات المحلية

```bash
npm run simulator:test
```

الاختبارات الحالية تتحقق من صحة السيناريوهات وحماية مسارات الانتقال والملفات ومكان حفظ لقطات الشاشة. قبل النشر، شغّل كذلك فحوص TypeScript وVitest وBuild للمشروع الكامل. لا يعتبر إنشاء الملفات أو نجاح الاختبارات المحلية إثباتًا أن المحرك اتصل بالموقع المنشور؛ ذلك يتطلب تشغيل الخدمة وضبط متغيرات الاتصال أولًا.
