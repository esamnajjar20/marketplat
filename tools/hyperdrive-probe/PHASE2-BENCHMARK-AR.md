# المرحلة الثانية — قياس Hyperdrive والتزامن

## الهدف والنطاق

هذه المرحلة تقيس سلوك `marketplat-hyperdrive-probe` تحت حمل صغير ومتدرج، بعد نجاح الاتصال الحقيقي بقاعدة Aiven في المرحلة الأولى. لا تغيّر هذه الأدوات خدمات Express أو Go أو Prisma، ولا تنفذ أي كتابة إلى PostgreSQL.

كل طلب اختبار يستدعي `POST /__internal/db-probe` المحمي، والذي ينفذ فقط:

```sql
SELECT 1::int AS ok;
```

لا تختبر هذه المرحلة عمليات CRUD أو استعلامات MarketPlat الفعلية. كما أنها لا تقارن اتصالاً مباشراً بقاعدة البيانات مع Hyperdrive؛ المقارنة المباشرة تحتاج إعداداً منفصلاً وضوابط مستقلة حتى لا تختلط نتائج الاختبار.

## ما أضيف

- `scripts/benchmark.mjs`: عميل قياس Node.js يستخدم HTTP Fetch لاختبار Worker المنشور.
- `scripts/benchmark.test.mjs`: اختبارات التحقق من إعدادات الحمل والإحصاءات وحدود التشغيل.
- `scripts/connection-snapshot.sql`: استعلام قراءة فقط لالتقاط عدد اتصالات PostgreSQL الحالية بقاعدة البيانات.
- `connectDurationMs` في استجابة المسبار: الوقت المستغرق في `client.connect()` عبر Binding الخاص بـ Hyperdrive.
- تقرير JSON محلي لكل تشغيل في `reports/`، وهذا المجلد مستثنى من Git افتراضياً.

## حدود الأمان المدمجة

| الحد | القيمة الافتراضية / القصوى |
|---|---:|
| مستويات التزامن الافتراضية | 1 ثم 2 ثم 5 |
| أقصى تزامن | 5 |
| الطلبات لكل مستوى | 20 افتراضياً، 50 كحد أقصى |
| طلبات التسخين | 2 افتراضياً، 3 كحد أقصى |
| مهلة كل طلب | 15 ثانية |
| إعادة المحاولة | لا توجد |
| نوع SQL | قراءة ثابتة فقط (`SELECT 1`) |

حتى عند ضبط جميع المستويات الخمسة والحد الأقصى للطلبات، لا تتجاوز الأداة 253 طلباً تقريباً في التشغيل الواحد (250 طلب مراحل + 3 طلبات تسخين). المستويات تعمل بالتتابع، ولا تعمل كل مستويات التزامن في وقت واحد.

تتوقف الأداة عن الانتقال إلى مستوى أعلى إذا فشل 10% على الأقل من طلبات المستوى، وبحد أدنى فشلين. إذا فشل أي طلب تسخين، لا تبدأ مراحل القياس.

يسمح التحقق المسبق بعناوين `*.workers.dev` و`localhost` فقط. لاستخدام نطاق HTTPS مخصص تمت مراجعته، يجب ضبط `ALLOW_CUSTOM_PROBE_HOST=true` صراحةً.

## المتطلبات

- Node.js ضمن المجال المحدد في `package.json` (`>=22.18 <25`).
- تثبيت الحزم عبر `npm ci`.
- Worker منشور ويعيد 200 من اختبار المرحلة الأولى.
- رمز `HYPERDRIVE_PROBE_TOKEN` محفوظ محلياً في متغير بيئة، وليس في الملفات أو سجل Git.

تحقق من نسخة Node قبل التنفيذ:

```bash
node --version
```

## التحقق قبل القياس

من مجلد `tools/hyperdrive-probe`:

```bash
npm ci
npm run check
npm run deploy
```

النشر مطلوب مرة واحدة لتفعيل حقل `connectDurationMs` الجديد في استجابة Worker. ينشر هذا الأمر Worker المسبار نفسه فقط؛ لا يغير Express أو Go أو مسارات الإنتاج. ثم عيّن عنوان نقطة الفحص والرمز في جلسة الطرفية الحالية. استبدل عنوان المثال بعنوان Worker المنشور لديك:

```bash
export HYPERDRIVE_PROBE_URL='https://<worker-subdomain>.workers.dev/__internal/db-probe'
export HYPERDRIVE_PROBE_TOKEN='ضع-الرمز-السري-محلياً-هنا'
```

لا ترسل الرمز في المحادثة، ولا تضفه إلى ملف `.env` متعقب أو إلى أوامر محفوظة في ملفات المشروع.

## تنفيذ الاختبار الافتراضي

```bash
npm run benchmark
```

التشغيل الافتراضي يقوم بطلبين للتسخين، ثم 20 طلباً عند كل مستوى من مستويات التزامن 1 و2 و5. يستغرق كل مستوى حتى يكتمل قبل بدء المستوى التالي.

يمكن تعديل حدود الاختبار داخل الحدود المسموحة:

```bash
BENCHMARK_REQUESTS_PER_LEVEL=30 \
BENCHMARK_WARMUP_REQUESTS=2 \
BENCHMARK_CONCURRENCY_LEVELS=1,2,5 \
npm run benchmark
```

لا ترفع الحمل لمجرد الحصول على رقم أعلى. ابدأ بالإعداد الافتراضي، وراجع اتصالات Aiven ومعدلات الفشل قبل أي تشغيل آخر.

بعد الانتهاء، أزل الرمز والعنوان من بيئة الجلسة:

```bash
unset HYPERDRIVE_PROBE_TOKEN HYPERDRIVE_PROBE_URL
```

## التقاط اتصالات PostgreSQL

لالتقاط عدد الاتصالات قبل الاختبار وأثناءه وبعده، نفّذ الاستعلام التالي في أداة SQL موثوقة متصلة بقاعدة Aiven، أو افتح الملف `scripts/connection-snapshot.sql` وانسخه:

```sql
SELECT
  current_database() AS database_name,
  clock_timestamp() AS captured_at,
  COALESCE(stats.numbackends, 0)::integer AS current_backend_connections
FROM pg_stat_database AS stats
WHERE stats.datname = current_database();
```

سجّل النتائج الثلاث مع التوقيت. أثناء تشغيل benchmark، راقب أيضاً مقياس الاتصالات في لوحة Aiven إن كان متاحاً. `numbackends` لقطة آنية لعدد الـ backends المتصلة بقاعدة البيانات المحددة؛ لا يمثل وحده عدد الاتصالات التي أنشأها Worker أو عدد الطلبات الجارية.

## قراءة التقرير

ينشأ ملف JSON في `reports/phase2-<timestamp>.json` ولا يضاف إلى Git تلقائياً.

| الحقل | ما يقيسه |
|---|---|
| `clientLatencyMs` | الزمن من جهاز الاختبار حتى استلام استجابة Worker كاملة؛ يتضمن الشبكة ووقت Worker |
| `workerConnectDurationMs` | الزمن الذي سجله Worker في `client.connect()` عبر Hyperdrive |
| `workerQueryDurationMs` | زمن تنفيذ `SELECT 1` ذهاباً وإياباً من خلال عميل PostgreSQL |
| `workerTotalDurationMs` | الزمن داخل Worker من قبل الاتصال حتى اكتمال الاستعلام، قبل إغلاق العميل |
| `requestsPerSecond` | عدد محاولات HTTP مقسوماً على زمن المرحلة |
| `p50` / `p95` / `p99` | المئينات 50 و95 و99 للقياسات الناجحة |
| `failureRatePercent` | نسبة الطلبات الفاشلة في المرحلة |

القيم الصغيرة في اختبار `SELECT 1` لا تتنبأ مباشرة بزمن استعلامات التطبيق الحقيقية. كما أن قياس HTTP يتأثر بموقع جهاز الاختبار والشبكة، لذا قارن تشغيلات من نفس البيئة قدر الإمكان.

## شروط قبول أولية

لا تعتمد نتيجة الأداء من تشغيل واحد. اجمع ثلاث تشغيلات بالإعداد الافتراضي مع تسجيل اتصالات Aiven قبل وأثناء وبعد كل تشغيل. تعتبر المرحلة صالحة للتحليل عندما:

- تنجح طلبات التسخين كلها.
- لا توجد أخطاء 401 أو 5xx أو مهلات.
- لا يظهر ارتفاع متواصل وغير مفسر في اتصالات قاعدة البيانات بعد انتهاء الحمل.
- لا تصل اتصالات قاعدة البيانات إلى حد الخدمة أو حد Hyperdrive المهيأ.
- تكون نتائج p50 وp95 ومعدل الطلبات متقاربة نسبياً بين التشغيلات.

هذه شروط لجمع بيانات موثوقة وليست ضماناً بأن Hyperdrive حسن أداء تطبيق MarketPlat. قرار ربط خدمات الإنتاج يحتاج اختباراً مستقلاً لاستعلامات التطبيق، ومراجعة توافق Prisma/Driver Adapter، وخطة تراجع.

## التراجع

هذه المرحلة لا تنشر Worker جديداً تلقائياً ولا تعدل إعداد Hyperdrive. لإيقاف الاختبار، أوقف الأمر الجاري في الطرفية. يمكن حذف تقارير JSON المحلية عند الحاجة؛ لا يؤثر ذلك على Worker أو قاعدة البيانات.
