# تدقيق طلبات صفحة «خدماتي» — 8 نوفمبر 2026

## النطاق

تمت مراجعة سجل Network المرسل لصفحة `/my-services` وربط الطلبات بمكونات الصفحة وReact Query وطرق تغيير التبويب/الفلاتر. الهدف إزالة طلبات البيانات المكررة وطلبات RSC التي لا تضيف بيانات جديدة، دون حذف طلبات يحتاجها المستخدم بعد فتح تبويب أو اختيار فلتر أو تاريخ.

## ما ثبت من السجل والكود

| الطلب | المصدر | القرار |
|---|---|---|
| `GET /service-listings/me?page=1&limit=10` | `MyServiceListingsList` في تبويب النظرة العامة | إبقاؤه؛ هذه قائمة إدارة الخدمات الفعلية، والصفحة تعرض حتى 10 عناصر مع البحث والحالات. |
| `GET /service-listings/me?page=1&limit=3&status=ACTIVE` | معاينة مختصرة أعلى لوحة `MyServicesHub` | أزيل؛ كانت تعيد تحميل أول 3 خدمات نشطة بينما قائمة الإدارة الكاملة تُحمّل في التبويب نفسه. |
| `GET /service-providers/me/analytics?period=all` | ملخص لوحة مقدم الخدمة / تبويب الإحصائيات | إبقاؤه؛ بيانات المؤشرات مطلوبة. كلا الموضعين يستخدمان React Query بالمفتاح نفسه وفترة `all`، فيُعاد استخدام الكاش بدل طلب مستقل ما دامت البيانات ضمن `staleTime`. |
| `GET /service-requests/incoming?page=1&limit=10` | تبويب الطلبات الواردة، فلتر «الكل» | إبقاؤه؛ بيانات القائمة مطلوبة عند فتح التبويب. |
| `GET /service-requests/incoming?...&status=PENDING/ACCEPTED/IN_PROGRESS` | نقر المستخدم على حالات مختلفة | إبقاؤها؛ كل اختيار يحتاج مجموعة نتائج مختلفة. أزيل فقط طلب RSC المصاحب لتغيير Query String. |
| `GET /appointments/me?page=1&limit=10` | تبويب المواعيد | إبقاؤه؛ لا يُطلب إلا عند عرض قائمة المواعيد. |
| `GET /appointments/availability/:providerId?date=...` | `AvailabilityCalendar` داخل نافذة حجز الموعد | إبقاؤه؛ التقويم يعرض التوفر ليوم واحد، وكل تاريخ مختلف يحتاج حالة توفر مختلفة. في السجل، تواريخ 8 و14 و22 نوفمبر مختلفة؛ لا يوجد دليل أنها إعادة طلب للتاريخ نفسه. |
| `GET /my-services?...&_rsc=...` | تنقل App Router | لم يُعتبر تكرارًا مؤكدًا بحد ذاته. طلبا RSC متقاربان لا يثبتان جلبًا مكررًا لبيانات الصفحة؛ يلزم عمود Initiator وسجل كامل يوضح هل سببهما تنقلان منفصلان أو prefetch أو إعادة تحميل. |

## التعديلات المنفذة

1. إزالة استعلام معاينة الخدمات الثلاث النشطة من `MyServicesHub` وإزالة واجهة المعاينة المكررة. قائمة إدارة الخدمات الكاملة بقيت في تبويب النظرة العامة.
2. إضافة `writeClientUrl()` إلى `frontend/lib/urlWithParams.ts` لتحديث Query String عبر History API على الصفحات التي تعتمد نتائجها على استعلامات العميل، دون بدء تنقل App Router/RSC لا يضيف بيانات من الخادم.
3. تحويل فلاتر الحالات في `useOwnedListPage`، المستخدمة من قوائم الإعلانات والمنتجات والخدمات المملوكة، إلى تحديث URL محلي مع إعادة الصفحة إلى الأولى.
4. تحويل فلاتر حالات الطلبات الواردة وتصحيح رقم الصفحة غير الصالح/الخارج عن النطاق إلى تحديث محلي للعنوان.
5. تحويل البحث والفلاتر وتصحيح الصفحة في `MyServiceListingsList` إلى تحديث محلي للعنوان، مع مزامنة قيمة البحث مع `useSearchParams` عند الرجوع للأمام/الخلف.
6. تحويل ترقيم الصفحات في `IncomingServiceRequestsList` و`AppointmentsList` و`MyServiceListingsList` إلى تحديث محلي اختياري عبر `clientSideNavigation` في مكوّن `Pagination`. بقي السلوك الافتراضي لبقية الصفحات دون تغيير.
7. إضافة اختبارات وحدات للتحديث المحلي للعنوان، وترقيم الصفحات، وفلاتر الطلبات، وعدم إظهار معاينة الخدمات المكررة.

## ما لم يتم تغييره عمدًا

- لم تُحذف طلبات API عند تغيير فلتر حالة الطلبات؛ لأن `PENDING` و`ACCEPTED` و`IN_PROGRESS` نتائج مختلفة وليست نسخًا من الطلب نفسه.
- لم تُحذف طلبات توافر المواعيد؛ فهي تأتي من نافذة حجز الموعد وتحتاج التاريخ المحدد. الـ endpoint المتاح في الكود يعيد يومًا واحدًا، وليس نطاق تواريخ دفعة واحدة.
- لم يُحذف طلب `appointments/me` أو تحليلات مقدم الخدمة أو قائمة الخدمات الأساسية.
- لم تتغير إعدادات نظام warming/preloading، احترامًا لقرار المشروع السابق إبقاءه معطّلًا.
- لم تُجرَ معالجة تخمينية لطلبي RSC الأوليين؛ يلزم حقل Initiator في DevTools لإثبات مصدرهما قبل تعديل تنقل Next.js.

## طريقة التحقق بعد الدمج

بعد نشر التعديلات، أعد فتح `/my-services` وسجّل Initiator لكل طلب. المتوقع ألا يظهر بعد ذلك طلب `service-listings/me?limit=3&status=ACTIVE`. وعند تغيير حالة الطلبات أو صفحات القوائم، يجب أن يتغير Query String وتُحدّث بيانات React Query دون طلب `my-services?_rsc`. أما فتح تبويب المواعيد، واختيار تواريخ مختلفة في نافذة الحجز، وتغيير حالة الطلب إلى قيمة مختلفة، فستظل تنتج طلبات API اللازمة.
