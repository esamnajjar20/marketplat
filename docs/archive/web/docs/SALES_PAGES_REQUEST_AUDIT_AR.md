# تدقيق طلبات صفحات المبيعات وإصلاحاتها

تاريخ التدقيق: 2026-11-08

## ملخص السجل الذي أرسله المستخدم

السجل أظهر طلبات متعددة من صفحات المبيعات، وأبرزها:

- `GET /sales/dashboard` يعيد `500` عدة مرات.
- `GET /sales/summary?period=month` ينجح بالتزامن مع طلب لوحة المبيعات.
- `GET /api/v1/sales/{id}/receipt` على نطاق الواجهة الأمامية يعيد `404`.
- طلبا RSC للوحة المبيعات وطلبا RSC لمسار الإيصال.
- طلبات التقارير والديون والعملاء والأقساط والتكلفة والتحليلات الذكية.

## الإصلاحات

### 1. خطأ لوحة المبيعات 500

راجعت مسار `salesService.dashboard()` وصولًا إلى `salesRepository.topProducts()`.
كان الاستعلام يختار العنوان من تعبير `CASE` بحيث يعيد `si.title` خامًا في أحد الفروع، بينما التجميع لا يحتوي على نفس التعبير الخام، بل على تعبير `CASE` آخر. هذا لا يفي بمتطلبات PostgreSQL لتجميع الأعمدة ويمكن أن يفشل برسالة `column must appear in the GROUP BY clause or be used in an aggregate function`، وبذلك يفشل endpoint كاملًا حتى لو نجحت بقية استعلاماته.

أصبح العنوان `MAX(si.title)`، مع الإبقاء على التجميع حسب `productId`، وحسب العنوان فقط عندما يكون `productId` فارغًا. هذا يحافظ على المقصود:

- صفوف المنتجات المرتبطة تُجمع حسب `productId`.
- المبيعات التاريخية التي لم يعد لها `productId` تُجمع حسب عنوان البيع المحفوظ.
- لا تتغير طريقة حساب الكمية أو الإيراد أو الربح أو حد النتائج.

أضفت اختبارًا يحمي شكل SQL وقيم sellerId وlimit ونتائج التحويل.

**حد التحقق:** لا تتوفر سجلات PostgreSQL/Render من وقت الخطأ داخل الأرشيف، لذلك لا يمكن إثبات أن هذا هو الاستثناء الذي سجله الإنتاج. لكنه عيب SQL ملموس في الاستعلام الذي ينفرد به endpoint لوحة المبيعات، ويجب التأكد بعد النشر من اختفاء 500. إذا استمر، يجب أخذ stack trace من سجل الباك إند لتحديد الاستعلام الآخر المتسبب.

### 2. إيقاف إعادة المحاولة التلقائية المكلفة لخطأ لوحة المبيعات 500

- عطّلت retry التلقائي في TanStack Query لهذا الاستعلام تحديدًا.
- منعت Axios من إعادة طلب هذا endpoint تلقائيًا عند HTTP 500، مع الإبقاء على إعادة المحاولة لأخطاء الشبكة و502/503/504.
- أضفت زر إعادة محاولة يدويًا في واجهة لوحة المبيعات.
- أضفت `retryOnMount: false` حتى لا يتكرر الطلب بعد فشل سابق لمجرد فك وتركيب تبويب اللوحة.

هذا لا يخفي الخطأ ولا يعرض نجاحًا وهميًا؛ تظهر رسالة الخطأ ويبقى للمستخدم إجراء إعادة المحاولة.

### 3. إزالة طلب ملخص الشهر المكرر

كانت صفحة النظرة العامة تطلب:

- `/sales/summary?period=month`
- `/sales/dashboard`

لكن استجابة `/sales/dashboard` تحتوي أصلًا على `summary` للشهر الحالي. أزلت استدعاء `useSalesSummary('month')` من واجهة النظرة العامة، وأصبحت بطاقات الملخص ولوحة المبيعات تشتركان في مفتاح React Query نفسه: `queryKeys.sales.dashboard()`.

وبذلك لا نرسل طلب ملخص منفصلًا لنفس البيانات.

### 4. إصلاح 404 الخاص بالإيصال

كان `ReceiptPageClient` ينفذ `fetch('/api/v1/sales/{id}/receipt')` نسبيًا. هذا وجّه الطلب إلى `marketplat.esamnajjar6.workers.dev` (نطاق الواجهة)، بينما مسار API الموثق موجود على نطاق API المهيأ في `apiClient`.

أصبح الطلب يستخدم `salesApi.receipt(id, { signal })`، ويستفيد من:

- نطاق API الأساسي الصحيح (`API_BASE_URL`).
- تمرير `AbortSignal` عند مغادرة الصفحة.
- مفتاح كاش مشترك `queryKeys.sales.receipt(id)`.
- `staleTime` لخمس دقائق لمنع إعادة الجلب غير الضرورية عند العودة السريعة للإيصال.

كما أصبح مسار الـ API يرمّز معرف البيع بـ `encodeURIComponent`.

### 5. منع نقرات الإيصال المتكررة

أضفت حالة تنقل مؤقتة في أزرار فتح الإيصال بقسم الديون وصفحة الديون المستقلة. بعد أول نقرة، تُعطّل أزرار الإيصالات حتى يتم التنقل، لمنع النقر المزدوج من إطلاق انتقالين إلى مسار RSC نفسه.

## طلبات أبقيت عليها عمدًا

الطلبات التالية ليست تكرارًا بحد ذاتها، وتخدم أقسامًا مختلفة عند فتحها:

- `/sales` لقائمة المبيعات.
- `/customers` لقائمة العملاء.
- `/sales/debts` و`/sales/debts/summary` للديون.
- `/sales/installments/upcoming` و`/sales/installments/overdue` للأقساط القادمة والمتأخرة.
- `/sales/reports` للتقرير المصفّى.
- `/sales/cost-products` لإدارة تكاليف المنتجات.
- `/sales/smart-insights` للتحليلات الذكية.
- `/sales/chart` و`/sales/compare` للرسوم والمقارنات.

يبدو أن المستخدم تنقل بين هذه التبويبات خلال الفترة الزمنية للسجل، ولذلك لا يصح حذف طلباتها أو دمجها لمجرد ظهورها خلال أقل من دقيقة.

طلب `/sales/debts` الذي ظهر `ERR` ثم `200` قد يكون فشل نقل/محاولة إعادة ناجحة؛ لا توجد قرينة كافية أنه طلبان مستقلان من مكوّنين مختلفين.

## تحقق ما بعد النشر

افتح لوحة المبيعات ثم راقب Network:

1. يجب ألا يظهر `/sales/summary?period=month` منفصلًا من نظرة عامة.
2. يجب أن يظهر طلب واحد لـ `/sales/dashboard` عند أول فتح، وينبغي أن يرجع `200`.
3. عند فشل `500`، يجب ألا يعيد العميل الطلب تلقائيًا؛ تظهر إعادة المحاولة اليدوية فقط.
4. عند فتح الإيصال، يجب أن يذهب الطلب إلى نطاق API لا نطاق الواجهة، ويرجع `200`.
5. افتح زر الإيصال مرة واحدة أو انقر بسرعة مرتين؛ يجب أن يحدث انتقال واحد فقط.
6. لا تتوقع اختفاء طلبات الأقسام الأخرى عندما تفتح تبويباتها، لأنها بيانات لازمة لكل قسم.
