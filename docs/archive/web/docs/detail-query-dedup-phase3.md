# MarketPlat — المرحلة الثالثة: إزالة طلبات التفاصيل المكررة

## الهدف

منع طلبات GET التي يعيد المتصفح تنفيذها بعد أن تكون صفحة App Router قد جلبت بيانات الكيان بالفعل على الخادم، مع الحفاظ على صلاحيات البيانات الشخصية وسلوك الأوفلاين.

## ما تغير

### 1. تفاصيل المنتج

- صفحة `app/(public)/products/[id]/page.tsx` تستخدم نفس `getCachedProduct` الذي تشاركه `generateMetadata`، ثم تضع النتيجة في مفتاح React Query الدقيق `queryKeys.products.detail(id)`.
- أُضيف `HydrationBoundary` حول `ProductDetailSection`.
- `useProduct` يحفظ نتيجة طلب المتصفح الناجح داخل `queryFn`، ويحفظ بيانات SSR المُرطّبة مرة واحدة بعد mount لأن Hydration لا ينفذ `queryFn`.
- لا يعيد ختم Snapshot قديمة عندما تُستخدم كـ fallback بعد فشل الشبكة؛ وهذا يمنع تمديد صلاحيتها دون تحديث حقيقي.
- يحافظ ذلك على شكل `ProductWithFullStore` الحالي، بما في ذلك تدفق تعديل المنتج الذي يستخدم مفتاح الاستعلام نفسه.

### 2. تفاصيل المتجر

- `StoreStorefront` يمرر `storeType` الذي وصله من Server Component مباشرة إلى `StoreProducts` في تبويبي المنتجات والعروض.
- أزيل `useStore(storeId)` من `StoreProducts`؛ لم تكن الشبكة تحتاج كيان المتجر، بل تسمياته فقط.
- أضيف `StoreVisitSnapshot` كجسر عميل صغير يحفظ بيانات المتجر العامة التي وصلت من SSR في مخزن الزيارات دون اتصال، مستخدماً مقطع الرابط الفعلي سواء أكان UUID أم slug. لا يستبدل هذا مسار الحفظ عند نجاح جلب المتصفح، ولا يحوّل Snapshot قديمة إلى نسخة حديثة.
- مسار `StoreDetailClient` الاحتياطي عند فشل جلب الخادم ما زال يستخدم `useStore`؛ تُحفظ النسخة عند نجاح طلب الشبكة فقط. إذا أعاد hook Snapshot قديمة كـ fallback، فلا يعاد ختم وقت صلاحيتها.

### 3. تفاصيل الطلب

- `requests/[id]/layout.tsx` يستخدم `React.cache()` لمشاركة قراءة الطلب بين `generateMetadata` والـ Layout، ثم يهيئ مفتاح `queryKeys.requests.detail(id)` عبر `HydrationBoundary`.
- قراءة الخادم مجهولة الهوية؛ لذلك لا تحوي العروض الخاصة. تحقق التدقيق من `serverApiAdapter` ومن قواعد `requestsService.getById`: صاحب الطلب يرى كل العروض، مقدم العرض يرى عرضه فقط، والزائر لا يرى عروضاً.
- يظل `useRequestDetail` مفعّلاً دائماً: الزائر يعيد استخدام بيانات SSR الحديثة ولا يكرر GET، لكن المتصفح يستطيع جلب البيانات عندما يفشل SSR أو تصبح النسخة قديمة.
- المستخدم المسجل يستخدم `staleTime: 0` للحصول على نسخة العروض المصرح بها من طلب المتصفح. عند فشل التحديث، تبقى البيانات العامة ظاهرة، وتظهر رسالة توضح أن بيانات الحساب لم تُحدّث، ولا تظهر قائمة العروض أو أدوات تقديم العرض حتى ينجح التحقق.
- تسجيل الخروج يمسح QueryClient عبر `cancelAndClearQueryClient` لمنع بقاء بيانات عرض خاصة بين الجلسات.

### 4. الصفحات التي لم تحتج تعديلاً

- تفاصيل الإعلانات كانت تستخدم Server Prefetch وHydrationBoundary بالفعل.
- تفاصيل الخدمات تستقبل بيانات القائمة من Server Component ولا تعيد جلبها في مكون التفاصيل.
- الملف الشخصي يستقبل بيانات المستخدم من الخادم، مع مشاركة الجلب بين metadata والصفحة.

## التحقق

شغّل:

```bash
cd frontend
npm run detail:dedup-phase3-audit
```

أُضيفت اختبارات وحدات لـ `useProduct` و`useRequestDetail`، واختبار لمكون `StoreVisitSnapshot`، وتم توسيع اختبار `useStore` للتحقق من حفظ نسخة المتجر عند الجلب الاحتياطي من المتصفح.

## حدود التحقق في بيئة إعداد هذه الحزمة

اجتازت فحوص المصدر الساكنة وفحص صياغة TypeScript/TSX. لم تتوفر `frontend/node_modules` في بيئة إعداد الحزمة، لذلك لم يتم تشغيل Vitest أو Next.js production build أو `tsc --noEmit` الكامل أو اختبار متصفح فعلي. يجب تشغيل هذه الأوامر في بيئة المشروع قبل اعتماد النشر.
