# تحسين طلبات الإعدادات والحضور — المرحلة

## نتائج فحص Network

- `/settings` يعرض تبويبًا نشطًا عبر `SettingsTabsHub`، ومحتوى التبويب يُنشأ من `renderTab`؛ أقسام الملف/الأمان/الجلسات/الإشعارات/المحظورين ليست استعلامًا واحدًا متكررًا.
- `/blocked-users?limit=100` خاص بقائمة المحظورين ولا يُستخدم كقائمة عامة داخل المحادثات.
- `/auth/sessions` خاص بعرض الجلسات النشطة.
- `/users/me` مطلوب لحقول الملف الكامل (مثل النبذة والهاتف) غير الموجودة في لقطة المستخدم المختصرة.
- `/service-types` هو قاموس أنواع الخدمات، بينما `/service-providers/me/service-types` هو اختيار مقدم الخدمة؛ النتيجتان مختلفتان.
- `AdminScriptConsole` و`AdminDeveloperToolsControl` يشتركان في `loadAdminDeveloperToolsSetting`، مع Promise واحدة أثناء التحميل وكاش خمس دقائق. طلب 2331ms ليس تكرارًا من الكود؛ إنه زمن استجابة endpoint/DB يحتاج قياسًا من الخادم.

## الإصلاحات

1. `PresenceHeartbeat` يمنع بدء PATCH آخر إذا كان طلب الحضور السابق ما زال قيد التنفيذ، بما في ذلك أحداث استئناف الصفحة/الشبكة.
2. خدمة الحضور في API تكتب مفتاح online ومفتاح last-seen عبر Redis pipeline؛ نفس الأمرين ونفس قيم TTL، لكن رحلة شبكة واحدة إلى Redis بدل رحلتين متوازيتين.
3. تحديث اختبار `presence.touch` للتحقق من pipeline ومعالجة أخطاء Redis.

## ما لم يتغير ولماذا

لم تُحذف طلبات الملف الشخصي أو الجلسات أو المحظورين أو قاموس الخدمات؛ لكل منها بيانات مختلفة وتُستخدم في القسم المعني. لم أضع كاشًا طويلًا على إعداد أدوات المطور لأن تغييره يجب أن ينعكس بسرعة على حسابات الإدارة الأخرى، كما أن قياس 2331ms وحده لا يثبت أن قاعدة البيانات هي السبب.

## التحقق

شغّل من `frontend`:
`node scripts/settings-presence-performance-audit.mjs`

لم تُشغّل اختبارات Jest أو TypeScript أو بناء Next.js في بيئة التعديل لعدم توفر `node_modules`. يلزم بعد النشر مراقبة زمن PATCH ووقت endpoint الإعدادات؛ التحسين هنا يقلل round trips داخل Redis ويمنع تداخل heartbeat، ولا يثبت وحده أن زمن API انخفض إلى رقم محدد.
