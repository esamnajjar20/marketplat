# تجربة Go الأولى في MarketPlat: تنظيف أحداث التحليلات

## ماذا تغيّر؟

أُضيفت خدمة Go مستقلة اختيارية لتنفيذ مهمة `report:cleanup-analytics` الموجودة أصلًا. بقي Express هو الباك إند الأساسي، وبقي تنفيذ Prisma القديم موجودًا ويعمل كمسار احتياطي.

- إذا لم تضبط `GO_WORKER_URL` و`GO_WORKER_TOKEN`، يعمل السكربت كما كان قبل التعديل.
- إذا كانت خدمة Go متاحة، يرسل إليها السكربت مهمة تنظيف أحداث التحليلات القديمة مع `retentionDays` المأخوذة من إعداد Express؛ بذلك لا تختلف سياسة الاحتفاظ بين المسارين.
- إذا تعذّر الاتصال أو فشلت الخدمة، يعود السكربت إلى تنفيذ Express/Prisma الأصلي.
- إذا ردت Go بالرمز `409` فهذا يعني أن عامل Go آخر يشغّل المهمة بالفعل؛ عندها لا يبدأ Express تنفيذًا متزامنًا مكررًا.
- الحذف يبقى على دفعات محدودة، ويمكن إعادة تشغيل المهمة بأمان.
- ترفض Go الطلبات غير الموثقة، والـ JSON غير الصحيح، ومدة الاحتفاظ خارج النطاق `1..3650` يومًا.
- مهلة تنفيذ Go أقصر من مهلة اتصال Express قليلًا، لإتاحة فرصة لإرجاع خطأ وتحرير قفل المهمة قبل بدء المسار الاحتياطي.

## إعداد النشر

1. انشر `apps/go-worker` كخدمة مستقلة من المستودع نفسه، باستخدام Dockerfile الموجود داخل المجلد.
2. اضبط `GO_WORKER_DATABASE_URL` على عنوان PostgreSQL مباشر يدعم session-level advisory locks؛ إذا لم تضبطه، تستخدم الخدمة `DIRECT_URL` ثم `DATABASE_URL`. لا تستخدم رابط transaction pooler لهذه الخدمة، ولا تفتحها على الإنترنت العام دون حماية شبكية.
3. أنشئ سرًا عشوائيًا طويلًا وضع القيمة نفسها في `GO_WORKER_TOKEN` لخدمة Go ولخدمة API.
4. اضبط `GO_WORKER_URL` في API على العنوان الداخلي لخدمة Go، مثل `http://go-worker:8081` في شبكة Docker أو عنوان الخدمة الخاص داخل منصة الاستضافة.
5. احتفظ بـ `ANALYTICS_RETENTION_DAYS=90` ما لم يكن هناك قرار واضح لتغيير سياسة الاحتفاظ.
6. راقب السجلات ومدة المهمة واستهلاك PostgreSQL قبل تعميم النمط على مهام أخرى.

## حدود التجربة

هذا التغيير يفصل تنفيذ مهمة الصيانة عن عملية Express، لكنه لا يجعل حذف PostgreSQL أسرع تلقائيًا؛ فالوقت الأكبر قد يبقى داخل قاعدة البيانات. كذلك، فشل Go بعد حذف بعض الدفعات قد يؤدي إلى إكمال ما تبقى بواسطة Express؛ وهذا آمن من ناحية البيانات لأن الشرط نفسه يعيد استهداف السجلات القديمة فقط، لكنه قد يسبب حملًا إضافيًا مؤقتًا. راقب قاعدة البيانات في أول تشغيل فعلي.

لم يتم تفعيل خدمة Go تلقائيًا في الإنتاج، ولم تُنقل بقية المهام أو مسارات API. يجب نشر الخدمة وضبط متغيرات البيئة صراحةً لتفعيلها. تغطي الاختبارات المتاحة منطق الدفعات، والتحقق من التوثيق والمدخلات ورؤوس الأمان دون قاعدة بيانات حقيقية. تعذر إكمال بناء الخادم واختبارات التكامل في بيئة التطوير الحالية لعدم توفر الاتصال بتنزيل اعتماد `pgx`؛ يجب تشغيل `go mod tidy` ثم `go test ./...` في بيئة متصلة، ثم تجربة المهمة على قاعدة اختبار، قبل نشر الخدمة.
