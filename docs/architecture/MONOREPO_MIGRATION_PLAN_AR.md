# خطة تحويل MarketPlat إلى Monorepo — سجل التنفيذ

## الهدف غير القابل للتفاوض

- الاحتفاظ بموقع Next.js الحالي وتطويره دون حذفه أو استبداله.
- الاحتفاظ بخادم Express/Prisma وقاعدة البيانات الحالية.
- إضافة تطبيق React Native مستقل لاحقًا، ومشاركة العقود والمنطق المناسب فقط.
- إبقاء تطبيق Capacitor الحالي وملفات Android ضمن المشروع إلى أن يتم تقييم البديل وإثبات التكافؤ؛ لا حذف تلقائي.
- عدم اعتبار أي مرحلة مكتملة قبل اجتياز بوابة التحقق الخاصة بها.

## المرحلة 0 — فحص الحزمة المرفوعة

- تم التحقق من سلامة ZIP: لا يوجد خطأ CRC.
- تحتوي الحزمة على مجلدي `apps/web/` و`apps/api/` مستقلين، ولكل منهما `package.json` و`package-lock.json`.
- لا يوجد مجلد `.git/` في الحزمة؛ لذلك لا يمكن إثبات حالة Git أو تاريخ النقل من الملف وحده.
- توجد إعدادات نشر واختبار تعتمد على المسارات الحالية، ومنها GitHub Actions وDocker وCloudflare وCapacitor/Android.
- توجد سياسة كاش مشتركة ونسخ متزامنة منها؛ يجب إبقاء اختبارات التوافق الحالية خلال أي استخراج لحزم مشتركة.
- توجد ملفات جذر تبدو كآثار أو مخرجات أدوات/طرفية. لا تُحذف في هذه المرحلة لأن غياب Git يمنع التأكد من كونها غير متتبعة أو غير مطلوبة.

## المرحلة 1 — تأسيس مساحة العمل بأقل مخاطرة

- أُضيف ملف الجذر `package.json` مع أوامر موحدة لتشغيل وفحص الويب والـ API.
- أُضيف `pnpm-workspace.yaml` مع إبقاء مجلدي المصدر الحاليين في مكانهما مؤقتًا، وإتاحة مجلدات `apps/*` و`packages/*` للخطوات القادمة.
- أُضيف فاحص بنيوي مستقل `tooling/verify-workspace.mjs`.
- لم تُنقل أو تُحذف ملفات التطبيق، ولم تُعدّل ملفات نشر الإنتاج في هذه المرحلة.
- لم يتم تثبيت التبعيات أو إنشاء `pnpm-lock.yaml` لأن الوصول إلى npm registry غير متاح في بيئة التنفيذ الحالية. لا تُعتبر التهيئة جاهزة للتثبيت الإنتاجي حتى تثبيت إصدار pnpm المتفق عليه وتوليد القفل والتحقق منه.
- فحص `node workers/cf-api-proxy/cache-policy.test.mjs` يفشل في النسخة الأصلية عند الاختبار `first warm populates every path`: القيمة الفعلية 14 والمتوقعة 13 (السطر 384). لم يتغير ملف الاختبار أو الـ worker في هذه المرحلة؛ سُجل هذا كفشل خط أساس يجب تحليله لاحقًا، لا كأثر من إعداد Monorepo.

## المرحلة 2 — خط الأساس قبل النقل

قبل نقل أي مجلد، يجب تشغيل وتسجيل نتائج:

1. `pnpm install --frozen-lockfile` بعد إنشاء ملف القفل رسميًا.
2. فحص TypeScript والـ lint واختبارات الويب.
3. فحص TypeScript والـ lint واختبارات الخادم، بما فيها الاختبارات التي تحتاج PostgreSQL.
4. Playwright smoke E2E والاختبارات المتعلقة بالعمل دون اتصال.
5. فحوص سياسة الكاش المشتركة، والبناء الخاص بـ Cloudflare، وبناء Capacitor/Android.

أي إخفاق سابق يُسجل كخط أساس ولا يُنسب إلى النقل دون دليل.

## المرحلة 3 — نقل محافظ إلى `apps/web` و`apps/api`

- النقل في المستودع الأصلي يجب أن يتم مع Git وبحركة قابلة للمراجعة.
- تحديث كل مسارات CI وDocker وCloudflare وCapacitor وPlaywright والسكربتات.
- إبقاء إعدادات النشر القديمة أو مسار رجوع صالح حتى نجاح اختبارات البناء والنشر.
- عدم نقل الكود إلى حزم مشتركة بالتزامن مع تغيير المسارات؛ فصل التغييرات يسهل اكتشاف الانحدارات.

## المرحلة 4 — الحزم المشتركة

- استخراج عقود API والتحقق المشترك عند وجود استعمال فعلي في تطبيقين على الأقل.
- عدم مشاركة مكونات واجهة الويب مباشرة مع React Native.
- نقل خوارزمية مفاتيح الكاش فقط بعد اختبارات تطابق byte-for-byte بين الويب والخادم والـ worker.

## المرحلة 5 — تطبيق React Native

- إنشاء تطبيق مستقل، مع دعم RTL والعربية، وتوثيق آمن، وتغطية اختبارية.
- إعادة استخدام API والعقود، لا إعادة استخدام واجهات Next.js.
- تنفيذ الميزات تدريجيًا، ثم بناء التخزين المحلي والمزامنة غير المتصلة مع ضمان idempotency وعدم فقد العمليات.

## بوابة النجاح النهائية

لا تُعتبر عملية Monorepo مكتملة بمجرد وجود ملفات إعداد الجذر. يجب أن يظل الويب قابلًا للبناء والنشر، ويظل الـ API قابلًا للبناء والاختبار، ويعمل تطبيق الموبايل الجديد، وتنجح اختبارات التكامل وE2E، وتكون إجراءات النشر والتراجع موثقة.

- لم تُحوّل استيرادات الويب أو الـ API إلى الحزمة بعد؛ يلزم أولًا إنشاء `pnpm-lock.yaml` وتشغيل TypeScript واختبارات عينات حقيقية من استجابات API. هذا الفصل مقصود لتجنب إدخال اعتماد غير متحقق في تطبيقات الإنتاج.
- لم يُنشأ تطبيق React Native في هذه الخطوة؛ إنشاء التطبيق يأتي بعد توحيد التثبيت وفحص توافق المسارات والاعتمادات.

## المرحلة 5 — ربط قائمة الإعلانات العامة في تطبيق الموبايل

- تمت مراجعة المسار الفعلي في `apps/api/src/routes.ts` و`apps/api/src/modules/ads/ads.routes.ts` و`ads.controller.ts`: القراءة العامة هي `GET /api/v1/ads`، والاستجابة الناجحة تستخدم `successResponse` مع قائمة في `data` وبيانات التصفح في `meta.pagination`.
- أُضيف عميل إعلانات للموبايل يستهلك المسار الحالي فقط؛ لم تتم إضافة أو تعديل أي route في الخادم.
- استُبدلت الحالة الفارغة التجريبية بقائمة إعلانات فعلية مع السعر والمدينة والتصنيف والصورة الأولى إن توفرت، وحالات تحميل/خطأ/إعادة محاولة/لا نتائج/السحب للتحديث.
- البحث عن الإعلانات يُرسل عند تأكيد البحث، لا مع كل ضغطة مفتاح، لتجنب طلبات الشبكة المتكررة على الاتصالات الضعيفة.
- بقيت بطاقات الأقسام تجريبية ولا تُرسل معرّفاتها إلى الخادم؛ لا توجد مطابقة مؤكدة بين معرّفات هذه الأقسام ومعرّفات التصنيفات الحقيقية.
- نجح الفحص البنيوي الثابت وفحص مساحة العمل. لم يُشغّل Expo/TypeScript ولم يُجرَ طلب حي إلى API؛ لذلك لا ندّعي نجاح بناء التطبيق أو التوافق التشغيلي قبل تثبيت الاعتمادات وضبط عنوان الخادم.

## المرحلة الثامنة — المصادقة الأولية للموبايل

تمت إضافة شاشة تسجيل دخول عربية وربطها بمساري الخادم الحاليين `POST /api/v1/auth/login` و`POST /api/v1/auth/logout`. تُحفظ بيانات المستخدم وAccess Token في الذاكرة فقط، ويُرسل CSRF token في رأس الطلب عند توفره. لا يُخزّن Refresh Token ولا يُفترض وجوده في JSON لأن الخادم يضعه في HttpOnly cookie.

**متبقي قبل الإنتاج:** تحديد وتطبيق آلية تجديد جلسة آمنة ومناسبة لتطبيق الهاتف، اختبار سلوك cookies وCSRF على Android/iOS، اختبار API حي، تشغيل TypeScript/Expo وبناء APK. لا تعتبر المرحلة مكتملة إنتاجيًا قبل هذه الفحوصات.

## المرحلة 9 — استعادة الجلسة والتخزين الآمن

- أضيف `expo-secure-store` لتخزين رمز الوصول قصير العمر وبيانات الجلسة اللازمة لاستعادة واجهة المستخدم، دون تخزين refresh token.
- عند بدء التطبيق، يحاول العميل `POST /api/v1/auth/refresh` مع `credentials: include` للاستفادة من Cookie التجديد HttpOnly التي يديرها الخادم، ثم يحفظ رمز الوصول الجديد عند وجود ملف مستخدم محفوظ.
- تمت إضافة انتهاء صلاحية محلي، والتعامل مع فشل الشبكة، ومسح الجلسة الآمنة عند الخروج.
- لم يُثبت بعد سلوك Cookie على Android/iOS؛ يجب إجراء اختبار حي لكل منصة مع إعدادات CORS وCookie الفعلية قبل اعتبار تجديد الجلسة جاهزًا للإنتاج.

## المرحلة العاشرة — حراسة استعادة الجلسة
- أضيفت آلية single-flight لتجديد الجلسة حتى لا تبدأ عدة طلبات refresh متزامنة من العميل نفسه.
- وثّقنا أن `/auth/refresh` معفى صراحة من CSRF في الخادم، لأن التطبيق بعد إعادة التشغيل قد لا يمتلك قيمة CSRF الحالية؛ يعتمد المسار على Cookie التجديد HttpOnly.
- أضيف `scripts/verify-phase10.mjs` إلى اختبار تطبيق الموبايل للتحقق من عقد المصادقة والتخزين الآمن وتنظيف الجلسة.
- نجحت الفحوصات البنيوية للمرحلة 7–10 وفحص مساحة العمل وJSON. لم تتوفر الاعتمادات أو lockfile، لذا لم يتم تشغيل TypeScript أو Expo أو بناء Android، ولم يُختبر cookie jar حيًا.

- أضيف `verify-phase49.mjs` إلى سلسلة اختبارات الهاتف للتحقق من سلوك الحماية في المصدر.
- حدود التحقق: الاختبار عقد مصدر ساكن، ولا يحاكي SQLite/نظام الملفات أو سباقًا حقيقيًا بين عامل المزامنة والتنظيف. لم تُثبت التبعيات ولم يُشغّل TypeScript أو بناء Android.


## المرحلة 50 — التحقق من ملفات الصور لحظة المزامنة
- إضافة فحص وقت الإرسال لصور الإعلان المحفوظة: يتأكد النقل من أن URI ملف دائم `file://` وأن الملف موجود وليس مجلدًا، وحجمه أكبر من صفر ولا يتجاوز 5MB.
- يمنع الاعتماد على التحقق القديم وقت اختيار الصورة فقط؛ فقد تُحذف الملفات أو تصبح غير متاحة قبل عودة الاتصال.
- تظل عملية الطابور غير مؤكدة محليًا عند فشل التحقق أو الرفع، وتحتفظ بمعرّف idempotency نفسه لمحاولة الاستعادة دون تكرار الإنشاء إذا كان الخادم يدعم هذا العقد.
- أضيف `verify-phase50.mjs` لفحص عقد المصدر وربطه بسلسلة `npm test`.
- حدود التحقق: فحوصات المصدر لا تختبر Expo FileSystem أو الخادم الحقيقي. يلزم لاحقًا اختبار جهاز/محاكي وفحص TypeScript والبناء، كما يجب أن يعالج المنتج أخطاء الملفات المفقودة بواجهة تسمح بإعادة اختيار الصورة.
