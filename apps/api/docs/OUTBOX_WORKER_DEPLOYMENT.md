# نشر عامل Transactional Outbox والتحقق منه

`src/scripts/runOutboxWorker.ts` **عملية Node مستقلة** ولا تبدأ مع `server.ts`. إذا نُشرت خدمة الـ API وحدها
فكل عمليات المستخدم تنجح، لكن تتوقف بصمت: الإشعارات، أحداث النشاط، تنبيهات البحث المحفوظ،
وإبطال الكاش (Cache bump / Edge purge).

## 1) إنشاء الخدمة على Render

- النوع: **Background Worker** (وليس Web Service).
- نفس المستودع، ونفس **Root Directory** الخاص بـ `apps/api`، ونفس متغيرات البيئة التي تستخدمها خدمة الـ API
  (على الأقل `DATABASE_URL`, `REDIS_URL`, مفاتيح Push/FCM، و`CLOUDFLARE_*` إن كان الـ edge purge مفعّلًا).
- Build Command: نفس أمر بناء الـ API.
- Start Command: `npm run worker:outbox:prod`
- عدد النسخ: **1** كافٍ للبداية. العامل يحجز كل حدث بـ lease (120 ثانية) فتشغيل أكثر من نسخة آمن، لكنه غير ضروري.

> على خطة Render المجانية لا توجد Background Workers. البدائل: خدمة مدفوعة صغيرة، أو تشغيل العامل على جهاز/VPS
> مفتوح الاتصال بنفس قاعدة البيانات (`npm run worker:outbox:prod`)، أو Termux كما في `TERMUX_SETUP.md`.

## 2) التحقق بعد النشر (دون الحاجة لقراءة السجلات)

الـ API يكشف الآن فحصًا يعتمد على **أثر** العامل (عمر أقدم حدث متأخر)، لأن الـ API لا يرى عملية العامل نفسها:

```
GET https://<api-host>/health/outbox
```

| النتيجة | المعنى |
|---|---|
| `200` + `"status":"ok"` | لا يوجد حدث متأخر أكثر من 5 دقائق ولا dead-letter. |
| `503` + `"status":"degraded"` + `oldestDueAgeSeconds` كبير | العامل غير شغّال أو متوقف. تحقق من الخدمة. |
| `503` + `deadLetters > 0` | أحداث فشلت 25 مرة وحُجرت. راجع `outbox_events.last_error` ثم أعد جدولتها أو احذفها يدويًا. |
| `503` + `"status":"unknown"` | تعذر الوصول لقاعدة البيانات. |

- `oldestDueAgeSeconds` يحسب فقط الأحداث التي يستطيع العامل استلامها (بلا قفل، أو انتهت مدة القفل 120 ثانية). الحدث البطيء الذي يجدد العامل قفله دوريًا لا يُعدّ متأخرًا، فلا يظهر `503` خطأً أثناء عمل العامل.
- الفحص يقيس أثر العامل على الطابور؛ لا يثبت أن العملية تعمل وقت الخمول (لا أحداث جاهزة). لإثبات حياة العملية نفسها استخدم مراقبة Render للخدمة أو أضف heartbeat مستقلًا.
- الاستجابة: أعداد وأعمار فقط (`pending`, `oldestDueAgeSeconds`, `deadLetters`, `lastProcessedAt`) دون حمولة أو بيانات مستخدمين.
- لحصر الوصول عيّن المتغير `OUTBOX_HEALTH_TOKEN` في خدمة الـ API ثم أرسل `x-health-token: <القيمة>`.
- يمكن ربطه بـ UptimeRobot/Better Stack كمراقب كلمة مفتاحية `"status":"ok"`.
- النتيجة تُخزن 10 ثوانٍ في الذاكرة حتى لا يضغط المراقب على قاعدة البيانات.

## 3) اختبار تشغيلي كامل (مرة واحدة بعد النشر)

1. سجل في السجلات سطر `Transactional outbox worker started`.
2. من حسابين: اجعل الحساب A يتابع متجر/بائع الحساب B، وانشر إعلانًا من B.
3. تأكد أن A يستلم إشعارًا (SSE أو Push) خلال ثوانٍ، وأن `/health/outbox` يبقى `ok`.
4. أوقف العامل لدقيقتين وانشر إعلانًا آخر: يجب أن يرتفع `oldestDueAgeSeconds`؛ بعد 5 دقائق يصبح الرد `503`. أعد التشغيل وتأكد أنه يعود `ok` ويصل الإشعار المتأخر.
